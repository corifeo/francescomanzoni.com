If you work with public vulnerability data, you will probably clean it before you can analyse it. The NVD, CISA's Known Exploited Vulnerabilities list, EPSS and CWE each publish in their own format, on their own schedule, with their own gaps. Someone has to join them, fix the dates and work out which record is current. Then the run takes so long that nobody wants to repeat it.

Data engineering has dealt with this problem for decades. Its usual shape is ETL: extract the data, transform it, and load it somewhere others can use it. The habits are old and mostly boring, and security does not use many of them. I think it should. This post argues for two of them, and shows what they look like in the tools I have built.

## Why I built VulnFlow

Two things drove it. The public feeds are messy, and a full run took long enough that people stopped repeating it. [VulnFlow](https://github.com/corifeo/VulnFlow) started as a way to do the cleaning once, in code, and reuse the result.

I had tried a version of this before. I published a consolidated dataset on [Kaggle](https://www.kaggle.com/datasets/francescomanzoni/vulnerability-management-datasets), covering the CVE, CISA KEV and EPSS feeds. There were not many consolidated datasets at the time, so a snapshot was useful. A snapshot is still fixed. It holds one view of the data, built one way, on the day it was made. An organisation that needs its own context cannot change how it was built, so the approach stops working for it.

The feeds also run out where the context begins. A public record describes the flaw. It does not say whether the flaw can be reached in your environment, whether attackers use it against systems like yours, or what the affected service does for the business. Tools fill those gaps for their customers, each with its own method.

I wanted something that could be run again, with each organisation's own logic added to it.

## Separate raw data from logic

Raw data is what the publisher gave you, unchanged. The NVD record for a CVE is raw data. Logic is everything you add on top: your own rating for a CVE, a rule for which sources you trust, or a flag for CVEs that need a second review. The two should not share a stored table.

The reason is practical. Logic changes, and when it does you rerun it from the raw data. If the raw data was overwritten with enriched values, you cannot tell what came from the publisher and what came from a rule. You cannot check the rule either, because its inputs have gone.

In VulnFlow, each stage has a name. Extractors read the feed. Transforms add attributes, normalise values or apply rules. Loaders write the result out, for example to Parquet, which a warehouse or lake can read. An organisation writes its own transform classes and keeps them under version control, next to the code that runs them. The core carries no risk scoring, so the weightings and rules are the organisation's, and so is the accountability for them.

## Enrich progressively, and make every run safe to repeat

Enrichment happens in stages. The raw feed comes first. A transform then adds the KEV listing, another adds your own rating for each CVE, and a third records the decisions already taken on it. Each stage reads the output of the one before it and writes something new. Nothing is changed in place.

That only works if each stage is idempotent. A step is idempotent when running it twice gives the same result as running it once. The idea is simple, and its consequence is sharp: a step that is not idempotent changes the data each time it runs, and nobody knows by how much.

I found this in my own build. The update recipe loaded the existing library, fetched the CVEs that NVD had modified, and merged the two with a plain concatenation. The merge did not check for duplicates, so every modified CVE appeared twice. That added about 12,000 rows, roughly 6% inflation in the counts for recent years. The recipe had no guard against a second run, so the same rows could be added again. The fix was an upsert keyed on the CVE identifier, where the newer record replaces the older one. Given the same input, the step now gives the same output.

For security, the point is about trust. A count that changes each time a job runs is not evidence. If a number on a dashboard cannot be reproduced from the raw feed and the rules, nobody should act on it.

## What security teams get

Security teams do not need to build a pipeline to benefit from one. They need to know what it can answer, and where its answers stop.

[VulnTriage](https://github.com/corifeo/VulnTriage) is one example built on the data. It takes a ranked queue and walks the analyst through the SSVC decision points, with the evidence shown beside each question. The analyst still makes the call. Mission and well-being depend on the organisation, and no public feed knows your assets. [VulnAnalyst](https://github.com/corifeo/VulnAnalyst) is another. It answers vulnerability questions from a local library, and it says when its data is partial.

Both are examples, not the point. The point is the layer underneath, which lets an organisation add its own logic without rebuilding the feed each time.

The context that matters most is the organisation's own view of each CVE: its rating, the sources it trusts and the decisions already taken. Those can be transforms, written and versioned by the organisation, and a weighting can live there too. Once it is code, someone has to own it, review it and explain it when it is wrong. That is the same accountability any control needs.

This is still a vulnerability database, not an asset inventory. VulnFlow does not know what runs where. Matching CVEs to assets is a separate job, done against the organisation's own asset records, and that match is where a list of what is actually exposed comes from.

## Vendors fill the gaps with scores

The feeds describe a flaw. They rarely describe your exposure to it. Whether a flaw can be reached from outside, whether attackers use it against systems like yours, and what the affected service does for the business all sit outside the public record.

Most tools do not hold that data either. A static analysis tool sees code, not a running system. Its customers still expect it to rank findings on its own, so the vendor publishes an exploitability score built from what the tool can measure.

Each vendor fills the same gaps with its own method. The same CVE can rank high in one product and low in another, and the difference comes from the methods, not from the organisation the scores are meant to serve.

I think firms should fill these gaps with their own data. Keep the raw sources unchanged, add the organisation's view of each CVE in transforms it owns, and build the scores, datasets and dashboards that teams use on top. Those outputs should give the same answer each time they run. Matching them to assets stays a separate step. A vendor score can be one input, but it should not decide the priority list. Until firms do this, the priority list will say more about the vendor than about the organisation.
